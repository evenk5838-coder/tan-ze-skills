# 方法论

## 看清对手

### 1. 定目的（先问这次分析为哪个决定服务）

| 目的 | 要回答 | 重点看 |
|------|--------|--------|
| 0→1 | 要不要做 | 市场规模、格局、有没有空白 |
| 1→N | 要不要迭代、先迭代哪个 | 对手功能、用户差评 |
| 对手出招 | 要不要跟 | 它为什么做、用户买不买账 |
| 定价 | 收多少钱 | 定价页、成本结构（AI 产品必看模型成本） |

### 2. 找竞品：四类都要列

- **直接竞品**：做一样的事，抢一样的人
- **间接竞品**：同一个需求，换一种方式满足
- **替代品**：用户现在怎么凑合（包括人工、Excel、搜索、问人）
- **潜在竞品**：有能力进来、还没进来（平台方、大厂、模型厂商）

AI 产品额外问：模型变强之后，这个产品更值钱，还是被基座模型/大平台吞掉？

### 3. 定维度：分层横向比

| 层 | 比什么 |
|----|--------|
| 市场层 | 蛋糕多大、什么阶段、谁在抢 |
| 定位 | 一句话定位 |
| 用户层 | 用户旅程、完整输出物、可感知的服务 |
| 技术层 | 流程、Agent/Workflow 分工 |
| 模型层 | 用了什么模型、为什么 |
| 基础层 | 数据来源、成本、定价 |

分层时不要把用户功能、技术能力、具体模型混在同一层。看不到的内部实现标【推测】。

### 4. 收信息

- 自己用一遍：注册、付费、走完主流程
- 应用商店 5 星与 1 星评价；社区吐槽帖、测评
- 官网定价页、财报；融资新闻、招聘 JD（看在投什么方向）
- 第三方数据平台
- 更新日志（看对手的取舍和演进）

纪律：每个数据标来源；AI 会顺着你说，不要只问"为什么我会成功"。

### 5. 下结论

- 若声称竞品“做不了/不愿做”，必须给出结构性证据，不能只说“我们做得更好”。证据不足时，描述本次聚焦的用户任务和差异化假设，说明需要怎样对照验证；不为了填公式编造竞品限制。
- 差异从用户、需求、场景三处找，往更垂直、更深、更专的方向破。
- 学成熟对手的做法，不比它的规模：只补适合自己、最重要、最紧急的部分。
- 结论落到"做 / 不做 / 差异化在哪"，不能停在罗列。

## 排出先后

### 0. 先问一句

这一版不做它，要验证的假设还成不成立？不影响就往后放。

### 1. Kano 分类

| 类型 | 特征 | 处理 |
|------|------|------|
| 基本型 | 没有就不满意，有了不加分 | 必须做 |
| 期望型 | 做得越好越满意 | 做差异化的地方 |
| 兴奋型 | 没有不扣分，有了惊喜 | 放一个即可 |
| 反向型 | 做了反而让人烦 | 坚决不做 |

### 2. 价值 × 成本四象限

| | 成本低 | 成本高 |
|---|---|---|
| 价值高 | 先做 | 排进规划 |
| 价值低 | 顺手做（或用来测试创新点） | 不做 |

- 价值：解决的痛点多疼、多高频、影响多少核心用户、对目标指标贡献多大。
- 成本：开发量、模型调用成本、数据构建成本、合规与集成难度。
- ROI 为负（投入持续大于产出）的不做；能接受短期亏损的必须写明换来的是什么（知名度、数据、留存）。
- 低开发难度不是 P0 的理由；P0 优先给核心用户的高频卡点。
- **全是 P0 等于没有优先级**。检查 P0 是否能构成可交付闭环，避免只凭分数定优先级。
- 用户已定义 P0/P1/P2 时沿用其口径。例如本次迭代可按 P0 核心闭环及必要质量底线、P1 闭环增强、P2 独立场景延展来判断；不是所有项目都固定采用此定义。
- 权重评分属于产品判断时标【假设】，写清维度和证据强弱；小样本的提及次数不等于总体需求频率。质量底线可以进入 P0，高分但场景独立的需求可以后移。

### 3. 定第一版：MVP

- 每一版都能用（滑板 → 自行车 → 汽车），不是先造轮子再造底盘。
- 三步：写下要验证的**一个**假设 → 只留验证它必需的 → 定通过标准（可量化、有时间）。
- 每条"必须做"都要连回一个痛点；每条"明确不做"都要写理由。
- 区分 POC（技术做不做得到，内部看）、原型（用户看不看得懂、想不想要）、MVP（真实用户会不会一直用）。AI 项目通常先跑 POC：拿真实数据看效果是否过门槛。

### 迭代规划额外项（类型 B）

- **取舍原则**：3–5 条，后续所有需求都按它判断；每条写"怎么判断"。
- **按承接方拆**：标注每条需求由谁承接、占不占瓶颈团队人力；瓶颈团队排满时，先启动不依赖瓶颈团队的需求，让有余力的团队先动。
- **有依赖顺序的先建基建**：例如质量优化前先建评价标尺和数据埋点，否则优化无方向。
- **版本节奏**：以外部锚点（关键上市/活动/出货日）倒推版本窗口，标注锁版、开发、上线日期。
- **砍需求顺序**：分 L0 绝不砍 / L1 优先保 / L2 可后移 / L3 先砍，写清为什么这样排。顺序是：先列需求 → 再谈资源 → 最后取舍。
- **未纳入本轮的需求**：分组列出并写不纳入原因，供后续查阅。

## 拍板立项

### 1. 三问决策矩阵（每问 1–5 分）

| 问题 | 等价于 | 看什么 |
|------|--------|--------|
| 用户买不买 | 市场有蛋糕吗 | 调研证据里的痛点强度、频次、现有凑合方式的代价 |
| 公司赚不赚 | 能赚到钱或换到什么 | 收入、成本节省、战略价值（知名度、数据、生态）；长期收益要写清链路 |
| 开发难不难 | 我们能做吗 | 现有能力复用、技术可行性、合规、集成、团队 |

结论：做 / 有条件做 / 先不做。

### 2. AI 多问四句（必答）

这些是内部分析问题，成稿时转换成方案、质量、风险和成本的陈述。

1. **该不该用 AI**：识别画面/语义变化、重复劳动、及时个性化建议等任务价值，以及标准化程度和现有方式的瓶颈。“重复性高、标准化程度高、人力瓶颈明显”是适合自动化的线索，不是所有 AI 产品必须同时满足的通用门槛。再比较规则、静态示例或流程改造的收益和成本；主观偏好由用户选择和确认，不伪装成唯一正确答案。再问：模型变强以后我们更值钱吗？
   - "有评分等级"不等于"标准一致"：人与人打分口径不一致时，先统一标准，AI 不能学未统一的评价。
   - 流程可穷举、稳定性要求高的场景优先评估 Workflow，不默认多 Agent。
2. **做到多好才算行**：门槛是多少（如准确率、延迟、一致性），跟人比怎么样。每个指标必须写清任务、样本、判定规则。
3. **出了错，谁兜**：AI、规则、人各管哪一段。低置信度、红线、临界情况、申诉转人工；涉及钱或高风险决定必须人确认。
4. **数据和成本**：数据从哪来、谁负责、权限与合规是否已批；用一次花多少（模型/语音调用），规模放大后成本曲线怎样；定价能否覆盖模型成本。

### 3. 投入测算

- 人力：角色 × 人数 × 周期 × 月成本
- 调用：单次成本 × 预估调用量（分试点期/推广期）
- 数据：采集、标注、清洗、评测集构建
- 其他：集成、存储、监控、采购
- 全部标【测算】并写口径；报价未定的写"待 Wx 报价后冻结"。

### 4. 分阶段闸门与条件立项

- 钱分阶段批：先批到第一个闸门（通常是离线评测）为止。
- 每阶段写：先验证什么 / 主要产出 / 不过闸怎么办（停止、降级、重做标准）。
- 典型顺序：问题基线与人工标准 → 离线/异步验证 → 实时或完整能力 → 小范围真实试点。
- 高风险场景用**影子模式**：AI 跟着跑、不做决定，与人工结果对比。
- 试点结束做 Go / Continue / Pivot / Stop 决策。
- 灰度（小范围放量验证效果与风险）与 A/B（控制变量比较方案）目的不同，不要混用。

### 5. 指标与收益口径

- 首期验收优先用过程指标（工时、等待时间、完成率、满意度、人-AI 一致性、错误/红线召回），收入类结果指标往往无法在首期证明因果，不作硬验收。
- 现状无数据的指标：写"随开发预埋，上线后建立基线"，不编目标值。
- 目标值尽量对齐可参照的现实水平（竞品实测、人工水平），说明"够得着"的依据。
- 业务方测算照写，但标【测算】、写来源和口径；相关数据（如对比组差异）写明分组、样本量、混杂因素，只说明"值得验证"。

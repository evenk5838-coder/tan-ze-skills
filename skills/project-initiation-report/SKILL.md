# 立项报告

立项 ＝ 拿证据换资源。报告要回答：值不值得投人、投钱，先做什么，什么情况下停。

本 Skill 覆盖第④站看清对手、第⑤站排出先后、第⑥站拍板立项。前三站（问题定义、用户调研、需求池）是输入，PRD 不在范围内。

## 工作方式

- **信息够了再写**。用户要求先讨论时，逐站澄清；已有明确确认和授权时，沿用结论继续完成，不重复追问。缺少会改变立项判断的信息时再问，不替用户编造事实。
- **证据分级**。所有数字和判断标注来源类型：【一手】用户原话/行为/埋点数据、【二手】网上公开资料（必须附链接）、【测算】估算或业务方测算、【假设】待验证。二手与一手分开写。
- **可以上网搜**竞品、定价、市场数据，但只用于补二手证据，每条附来源。
- 分批询问关键问题，可用当前环境提供的问答工具；不依赖固定工具名。
- **区分整体问题与本期范围**。整体问题先覆盖证据支持的主要需求簇，再说明本期选中的用户、场景和核心闭环；不能为了聚焦 MVP，把其余真实问题从背景或需求池中抹掉。
- **分析框架不等于成稿目录**。“三问矩阵”“AI 四问”“唱反调”等用于内部检查。正式报告改用用户价值、商业价值、实施可行性、AI 能力与质量要求、风险与停止条件等标题；仅当用户要求教学讲解时保留问答式框架。

## 流程

复制此清单并跟踪进度：

```
- [ ] 0. 判断立项类型 + 选文风
- [ ] 1. 输入检查（不过关就停）
- [ ] 2. 看清对手（竞品分析表）
- [ ] 3. 排出先后（Kano + 四象限 + MVP 范围表）
- [ ] 4. 拍板（三问矩阵 + AI 四问 + 投入测算 + 阶段闸门）
- [ ] 5. 唱反调 + 自检
- [ ] 6. 成稿与交付：按用户已确定的格式完成 Markdown / HTML / Word
```

### 0. 判断类型、选文风

问用户：
- **类型**：A. 0→1（新产品/新功能，核心问"做不做"）；B. 1→N 迭代规划（已有产品，核心问"先做哪些、按什么节奏"）。
- **文风**：给出 [styles.md](styles.md) 中的选项让用户选。

### 1. 输入检查

按 [checklist.md](checklist.md) 的「输入门槛」逐项核对用户材料。正式资源决策中，必备信息不足且会改变判断时，列出缺口及影响，先补齐。用户已明确这是课堂作业、模拟提案或允许假设时，可在其授权范围内继续，标出证据限制与待验证项，不能虚构访谈、版本状态、测试结果或报价。补充项缺失记入报告「数据与信息缺口」。

### 2. 看清对手

方法见 [methods.md](methods.md#看清对手)。顺序：定目的 → 四类竞品 → 定维度 → 收信息 → 下结论（差异化一句话）。

产出：竞品分析表 + 差异化判断（用户、核心价值、已有替代方式、本次机会与待验证优势）。没有结构性证据时，写“差异化假设”，不强称竞品做不了。已有用户确认时直接沿用。

### 3. 排出先后

方法见 [methods.md](methods.md#排出先后)。顺序：先问"不做它，要验证的假设还成立吗" → Kano 分类 → 价值 × 成本四象限 → 定 MVP。

产出：带优先级的需求清单 + MVP 范围表（要验证的假设 / 必须做 / 明确不做及理由 / 以后再说 / 通过标准）。
类型 B 额外产出：取舍原则（3–5 条，每条附"怎么判断"）、版本节奏表、资源不足时的砍需求顺序。

### 4. 拍板

方法见 [methods.md](methods.md#拍板立项)。
- 三问决策矩阵：用户买不买、公司赚不赚、开发难不难，各 1–5 分，附依据。
- 内部用 AI 四问检查完整性：使用 AI 的依据、效果门槛、失败兜底、数据和成本。成稿把答案融入方案、指标、风险与投入，避免把课堂问句照搬成章节标题。
- 投入测算：人 × 周期 × 人力成本 + 模型/语音调用 + 数据构建 + 其他，全部标【测算】。
- 分阶段闸门：每阶段验证什么、产出什么、不过闸怎么办；钱按阶段批。
- 结论只能是：做 / 有条件做 / 先不做。有条件做要写清条件和试点边界。

### 5. 唱反调 + 自检

1. 用 [checklist.md](checklist.md#唱反调) 中的提示词，让模型论证"为什么竞品会成功、而这个项目会失败"，把站得住的点写进风险，必要时回改结论。
2. 逐条过 [checklist.md](checklist.md#成稿自检)，不通过的改完再交。

### 6. 成稿

参考 [report-template.md](report-template.md) 组织必要内容，目录不是不可调整的格式。用户提供案例时，先识别其信息顺序、正文与附录分工、视觉版式，再结合当前项目重组；案例里的用户、收入、预算、人员、日期和判断不能成为本项目事实。

可采用“决策摘要 → 问题诊断 → 目标体验 → 取舍原则 → 专题方案 → 版本与资源 → 决策待办及风险 → 详细资料”的顺序。正文服务拍板；完整需求池、原话证据、评分依据和详细竞品资料放附录，保留来源链路。具体章节数、配色和导航样式跟随用户要求，不固定为某个案例。

Markdown 文件名 `立项报告-<项目名>.md`，保存位置沿用用户已指定的路径或当前项目约定。HTML、Word 已获授权就同步完成；未确定格式且会影响交付时再询问。修订已有报告时保留可恢复的原版，更新版本标识和跨章节引用；局部改动同步到所有已承诺格式。

HTML 可做单文件、目录导航、首屏决策摘要、重点数字及可展开附录，无外部依赖；长表格兼顾窄屏与打印。Word 使用相应文档技能并渲染检查分页。对 HTML 的显示和交互只报告实际验证结果；浏览器访问受限时如实说明，不能把静态检查说成浏览器验证。

修订多需求报告、参考案例重组或处理课堂框架表达时，按需阅读 [references/revision-method.md](references/revision-method.md)。它仅包含通用修订方法，不提供任何具体项目的事实、参数或预算。

## 边界

- 不写 PRD，不展开功能细节、交互和异常流程；只写到能拍板的粒度。
- 不把业务方测算写成结果；不把相关写成因果。
- 不为加 AI 而加 AI：AI 四问的第一问答不过，结论应为先不做或改用规则/流程方案。
- AI 不应拥有涉及钱、人事、正式认证等高风险决定的最终决定权，除非用户明确说明并写清兜底。
- 用户没提供的事实，不编造；标【假设】或问用户。
